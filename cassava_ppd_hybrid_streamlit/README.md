# Cassava PPD Hybrid Prediction System

**Project title:** A Hybrid Machine Learning and Time-Series Framework for Predicting Cassava Post-Harvest Deterioration Risk

Python + Streamlit implementation based on the supplied project document, especially the Chapter Three architecture: Bi-LSTM environmental forecasting followed by XGBoost deterioration-risk estimation.

## What the application does

1. Accepts linked environmental time-series and cassava batch/outcome CSV files.
2. Validates batch IDs, timestamps, numerical fields, binary outcome labels, and the required observation windows.
3. Uses the 24 hourly environmental observations immediately before harvest to forecast temperature and relative humidity for the next 72 post-harvest hours with a Bi-LSTM.
4. Converts the 72-hour forecast into summary features (mean, minimum, maximum, and hours above illustrative thresholds).
5. Combines those forecast features with cassava variety, mechanical-damage score, initial root condition, dry-matter percentage, and harvest hour.
6. Uses XGBoost to estimate the probability of the defined binary deterioration outcome. This probability is displayed as the Deterioration Risk Index (DRI).
7. Evaluates forecasting with MAE/RMSE and risk classification with accuracy, precision, recall, F1-score and ROC-AUC when defined.
8. Compares the Bi-LSTM forecast with a persistence baseline and compares XGBoost with a Random Forest risk-model baseline.

## Important time alignment and data requirement

To align the 72-hour forecast with a deterioration outcome measured 72 hours after harvest, each batch must have:

- 24 consecutive hourly environmental observations immediately **before** its harvest timestamp;
- 72 consecutive hourly environmental observations from harvest through the following 72 hours;
- one independently observed `ppd_status_72h` outcome for that same batch, assessed at the end of the post-harvest 72-hour period;
- a `harvest_timestamp` in the cassava outcome file.

The environmental and cassava files must use the same defensible `batch_id`. Do not join unrelated environmental and root records because their dates look similar. The application recommends at least 20 independent linked batches to create training, validation and test partitions. More batches are strongly preferred for credible model evaluation.

### Environmental CSV columns

- `batch_id`
- `timestamp`
- `temperature_c`
- `relative_humidity_pct`

### Cassava phenotype/outcome CSV columns

- `batch_id`
- `variety`
- `mechanical_damage` (numeric scale 0–3)
- `initial_condition` (e.g. Good, Fair, Poor)
- `dry_matter_pct`
- `ppd_status_72h` (0 or 1, defined consistently and independently observed)
- `harvest_timestamp` (date and time of harvest)

The current Chapter Three implementation forecasts temperature and relative humidity, matching its specified Bi-LSTM inputs. Oxygen is mentioned in the broader project scope where suitable records are available, but it is not currently used as a model input. Do not imply that oxygen is modelled by this version.

## Validation design and leakage controls

- Whole batches are sorted by harvest timestamp and divided chronologically into 70% training, 15% validation and 15% test groups.
- No batch appears in more than one partition.
- Scalers are fitted on training sequences only.
- Validation data are kept separate from final test evaluation.
- The forecast is aligned to the post-harvest 72-hour period, and the binary label must describe that same period.
- A simple persistence forecast is used as the transparent forecasting baseline. Random Forest is used as a baseline for the XGBoost classifier. SARIMAX/GRU are alternative methods identified in the research document but are not implemented in this initial application version.

The data split is chronological by batch harvest time. It is suitable when batches represent independent harvest/storage records. If multiple roots share one batch or storage unit, keep them together under one batch/group ID.

## Synthetic demonstration mode

The app includes generated synthetic data to demonstrate the complete software workflow. Synthetic outcome labels are generated by a simulated rule. They are not real cassava observations, and model scores obtained from them are not research findings or evidence of real-world predictive accuracy. Use real, independently labelled and time-aligned records for research validation.

## Run locally

Python 3.11 is recommended.

```bash
pip install -r requirements.txt
streamlit run app.py
```

TensorFlow CPU and XGBoost are substantial dependencies. Initial installation and model training may take several minutes. Training is CPU-based.

## Streamlit Community Cloud

1. Extract this ZIP file.
2. Push the contents of the `cassava_ppd_hybrid_streamlit` folder to a GitHub repository.
3. Create a Streamlit Community Cloud app and set `app.py` as the main file.
4. Wait for dependency installation and app startup.

No Supabase or separate backend is required. Data processing and model training occur in the Streamlit app process.

## Research limitations

- Model validity depends on enough real batches, reliable deterioration labels and correctly aligned environmental measurements.
- DRI is a model-estimated probability for the defined binary label, not a universal biological deterioration scale.
- The forecast thresholds (30°C and 80% RH) are feature-engineering choices for this prototype, not validated biological cut-offs.
- Oxygen is not currently modelled.
- The app does not connect to physical IoT sensors, classify root images, predict crop yield, or predict spoilage in processed fufu.
- Synthetic results must never be presented as measured real-world performance.
